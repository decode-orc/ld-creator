# AI Instructions for ld-creator

---

## 1. Overview & Core Constraints

### 1.1 Role & Scope
- You are a coding assistant for the **ld-creator** project.
- ld-creator modulates CVBS video, analogue audio and EFM into a LaserDisc RF
  signal per IEC 60856 (PAL) and IEC 60857 (NTSC). Its inputs come from the
  sister application **videosynth**; its output is decoded by **ld-decode**.
  The combination is a known-truth harness for measuring ld-decode's accuracy
  (see `docs-tech/design/high-level-design.md`).
- Follow these instructions **in addition to** any `.github/AGENTS.md` files in the task directory or above.
- For pull-request workflows, see the separate PR templates in `.github/PULL_REQUEST_TEMPLATE/`.

### 1.2 Git Operations
- **Do not** run `git add`, `git commit`, `git push`, `git stash`, or any command that modifies repository state unless the user explicitly requests it.
- Read-only commands (`git status`, `git log`, `git diff`, `git show`) are permitted.

### 1.3 Naming
- Never use planning-phase terminology (e.g., `phase0`, `mvp-phase`).
- Use **descriptive, domain-oriented names**: `video_fm_modulator`, `audio_subcarrier`, `pre_emphasis_filter`, `efm_pulse_width_mixer`, `rf_sample_writer`.

### 1.4 Content Restrictions
- Do **not** include advertisements, promotions, or commercial references.
- Omit "generated by", "co-authored by", or tool/service attributions.

## 3. Testing & Quality Assurance

### 3.1 Unit Testing
- Source of truth: `TESTING.md`.
- Unit tests are the **primary** methodology; prefer them for all new or modified behaviour.
- Requirements:
  - Mock dependencies; tests must be **deterministic**.
  - No filesystem, network, system clock, database, or external service dependencies.
  - Keep tests isolated and fast.
  - Use interface-based dependency inversion and constructor injection.
  - Name tests by behaviour, with no underscores (clang-tidy `google-readability-avoid-underscore-in-googletest-name`), e.g. `TEST(VideoFmModulatorTest, ProducesBlankingCarrierWhenGivenPalBlankingLevel)`.
- Classification:
  - Classification follows the **directory**: sources under `tests/unit/` are labelled `unit`, those under `tests/functional/` are labelled `functional`. There is no list to update.
  - Use `functional` **only** when the objective cannot be met with a unit test.
  - Tests touching the filesystem, real media, the built executable, or full pipelines **must** be `functional`.
  - Tests that run the pinned videosynth or ld-decode (round-trip tests) are `functional` and must skip cleanly when the tool is not on `PATH`.
  - A file whose tests would span both categories must be **split into two files**, one per tree.
- Fixtures: generated media (CVBS, WAV, EFM, RF) is **never** committed. Round-trip inputs are produced by the pinned videosynth from committed project YAML at test time, into the build tree.
- Output: tests and scripts must write generated media under the build directory, never into the source tree.
- CI: the default unit-test lane must stay fast and mocked; do **not** add functional tests to it.
- Independent verification: `scripts/` analysis tools share no code with ld-creator or ld-decode, run with `python3 -E -B` in the dev shell (`-B` keeps bytecode out of the source tree), and are developer checks, not ctest targets (TESTING.md, "Independent verification"). The one exception is the round-trip wrapper `tests/functional/test_round_trip.cpp`, which runs `scripts/round_trip.py` on the carrier diagnostic.

### 3.2 Logging
- **info**: normal lifecycle messages, stage transitions, validation summaries.
- **debug**: configuration details, branch decisions, resolved paths.
- **trace**: per-field, per-line, per-sample state, tight loops, intermediate values.
- Guidelines:
  - Use the least verbose level that still explains the behaviour.
  - Keep text concise and action-oriented for both console and file output.

## 4. C++ Coding Standards

### 4.1 Baseline & Tooling
- C++20 (`CMAKE_CXX_STANDARD 20`).
- Follow the [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html).
- **Never** use manual column-alignment (e.g. double-spacing before `=`, aligning continuation lines to opening parentheses) — clang-format will undo these and leave violations.
- Use static analysers (`clang-tidy`) and sanitizers where available in the Nix environment.

### 4.2 Source File Headers
- Every C++ source and header **must** start with an SPDX header **above** all other content.
- Template:
  ```cpp
  /*
   * File:        video_fm_modulator.cpp
   * Module:      modulation
   * Purpose:     Frequency-modulates the pre-emphasised video onto the main carrier
   *
   * SPDX-License-Identifier: GPL-3.0-or-later
   * SPDX-FileCopyrightText: 2026 Contributor Name
   */
  ```
- `File` must match the filename **exactly** (case-sensitive).
- `Module` must describe the logical component.
- `Purpose` must be a concise, domain-oriented description.

### 4.3 Custom Additions

#### 4.3.1 Interface Design
- Prefix abstract interface names with `I` (e.g., `ILogger`, `ICvbsFieldSource`, `IRfSampleSink`).
- Methods: `virtual` with `= 0` for pure virtual.
- Always include a virtual destructor: `virtual ~IInterfaceName() = default;`

#### 4.3.2 Memory Safety
- Prefer RAII: use smart pointers (`std::unique_ptr`, `std::shared_ptr`) for ownership.
- Use assertions for pointers that must **never** be null.
- Range-check container access; prefer `std::span` or bounds-checked methods over raw arrays.
- Document ownership semantics explicitly.

#### 4.3.3 Concurrency
- Document thread-safety guarantees for every public class or function.
- Use `std::mutex`, `std::atomic`, or message-passing; never rely on undefined behaviour.
- Mark shared vs thread-local state explicitly; prefer immutable data where possible.
- Output must be **deterministic**: byte-identical RF for the same inputs regardless of thread count.

#### 4.3.4 File Organisation
- Public headers live in `include/ld_creator/<module>/`; implementation in `src/<module>/`.
- Close namespaces with a trailing comment: `}  // namespace ld_creator`

#### 4.3.5 Constants & Clarity
- Avoid magic numbers; define named constants with descriptive comments.
- Reference authoritative specs when implementing standards (see §9.4).

#### 4.3.6 Specification References
- Format: `// <Organization> <Document>-<Section>: <description>`
- Examples:
  - `// IEC 60856-1986 9.2.2: PAL main carrier at blanking level is 7.1 MHz.`
  - `// IEC 60857-1986 8: NTSC audio channel I subcarrier is 146.25 fH.`
  - `// IEC 60857-1986 Amendment 2 13.1.2: EFM low-pass, -3 dB at 1.75 MHz.`
  - `// ITU-R BT.1700 Annex 1 Part B Table 1 item 1 (625-line PAL).`
- Supported organisations: IEC, ECMA, EBU, ITU-R, ITU-T, SMPTE.

#### 4.3.7 Commenting
- Use inline comments **above** function declarations for purpose, parameters, and return values when non-obvious.
- Explain the approach before complex algorithms (filters, modulators, resamplers).
- Document rationale behind non-obvious decisions.
- Use `// TODO(<owner>): <description>` (clang-tidy `google-readability-todo` rejects a bare `TODO:`); avoid redundant comments.

## 5. Performance

- **Profile before optimising**; prefer measurable gains over premature micro-optimisation.
- Minimise copies: use references, move semantics, and `const` where possible.
- Document Big-O complexity for public algorithms; note cache-locality assumptions where relevant.
- Flag any change that increases memory use by >10 % or execution time by >5 % for design review.
- RF output is produced at tens of megasamples per second; prefer streaming, block-based processing and SIMD-friendly contiguous buffers over per-sample virtual calls.

## 6. Development Environment

- The project uses **Nix**; the provided development shell is authoritative.
- Run normal workflows inside the project shell:
  `nix develop "git+file://$PWD" --command <command>`
  - Use `git+file://`, not `path:`. A `path:` reference copies the whole working tree, including `build/` and its generated media, into the Nix store on every call, and fills the disk. `git+file://` copies only tracked files.
  - `git add` a new file before `nix build` or `nix flake check` needs it; untracked files are invisible to them.
- The dev shell puts the pinned `videosynth` and `ld-decode` on `PATH`. Use those, not locally built copies, for round-trip work, so results are reproducible from `flake.lock`.
- Temporary tools (profiling, debugging, one-off analysis):
  - Use ad-hoc shells:
    `nix shell nixpkgs#<tool> --command <tool> <args>`
    `nix shell nixpkgs#<tool1> nixpkgs#<tool2> --command <command>`
- Do **not** modify `flake.nix` or `default.nix` solely for temporary dependencies.
- Do **not** update `flake.lock` (e.g. `nix flake update`) unless the user asks; a sister-tool bump changes the test baseline.
- Builds are **out of source**. CMake refuses an in-source configure; use `build/` (or `build-*/`).
- Always provide the Nix-based equivalent alongside plain shell commands.

## 7. Pre-Session Nix Setup
Before starting a session:
- Check available disk space using `df -h /nix/store`.
- If space is critically low (< 20% free), warn the user before proceeding.
- Create a temporary profile:
  ```bash
  export AI_AGENT_PROFILE=\$(mktemp -d)/nix-profile
  export NIX_USER_PROFILE_DIR=\$AI_AGENT_PROFILE
  ```

## 8. Post-Session Nix Cleanup
After completing a development session or task, perform the following steps to clean up the Nix store in the temporary profile:

  ```bash
  nix-collect-garbage -d -p \$AI_AGENT_PROFILE
  rm -rf \$AI_AGENT_PROFILE
  ```

## 9. Documentation & Specifications

Documentation is **part of the deliverable**, not a follow-up task. A change
that alters behaviour, options, file formats, or the build is incomplete until
the affected documents (§9.3) have been updated in the **same task**.

### 9.1 Documentation Layout

| Location | Contents | Audience |
|----------|----------|----------|
| `docs/` | MkDocs source for the published site (<https://decode-orc.github.io/ld-creator>): user manual and reference | End users |
| `docs-tech/design/` | `high-level-design.md` — the living design specification | Developers |
| `docs-tech/user/` | In-repository feature/design notes and implementation plans | Developers |
| `docs-tech/*-specification*/` | Specification submodules (CVBS format, analogue video and LaserDisc) — **read-only**, never edit | Reference |

| `BUILDING.md` | Build, run and documentation-build instructions | Developers |
| `TESTING.md` | Testing vision, strategy and repository rules | Developers |
| `AGENTS.md` | Contribution and coding standards (this file) | Agents |

Rules:
- `docs/` is **exclusively** the published site. Do not add design documents,
  implementation plans, notes, or submodules there.
- Anything developer-facing that is not the published site belongs under
  `docs-tech/`.
- Never edit the specification submodules; they are upstream sources.

### 9.2 Published Site Structure (`docs/`)
- Top-level sections, in navigation order:
  - `getting-started/` — installation and the quick-start walkthrough.
  - `user-manual/` — one page per subsystem; explains *what a feature does and
    how to use it*.
  - `reference/` — exact meaning, type, default and valid range of every CLI
    option, input file and output format.
  - `misc/` — troubleshooting, issue reporting.
  - `assets/` — logo, icons and `custom.css` only.
- Navigation is assembled by `awesome-nav` from `.nav.yml`. **Every new page
  must be added to its directory's `.nav.yml`**, or it will not appear in the
  site navigation.
- Page conventions:
  - Start with a single `#` H1 title matching the navigation entry.
  - Link between pages with relative `.md` paths (e.g.
    `../reference/cli-options.md`), never site URLs.
  - Use tables for key/option reference material, and `!!! note` / `!!! warning`
    admonitions for caveats.
  - Cite the governing standard inline where behaviour is spec-driven
    (e.g. `IEC 60856 §9.2.2`), matching the format in §4.3.6.
- New user-facing feature ⇒ a `user-manual/` page (or section) **and** the
  corresponding `reference/` entries.
- Verify the site still builds before finishing:
  `nix develop "git+file://$PWD" --command mkdocs build --strict`.
  Preview with `nix develop "git+file://$PWD" --command mkdocs serve`.

### 9.3 Keeping Documentation Current

When a change touches any of the following, update the listed documents in the
same task:

| Change | Update |
|--------|--------|
| New or changed CLI option | `docs/reference/cli-options.md`, `docs/user-manual/cli.md` |
| New or changed accepted input (CVBS preset, audio, EFM) | `docs/reference/input-files.md`; HLD (§9.5) |
| New or changed RF output format or modulation parameter | `docs/reference/rf-output.md`; HLD (§9.5) |
| New validation rule or error message | `docs/misc/troubleshooting.md` |
| New subsystem or pipeline stage | HLD (§9.5); a `docs/user-manual/` page if user-visible |
| Round-trip workflow change | `docs/user-manual/round-trip-testing.md`, `TESTING.md` |
| New directory, build dependency or build step | `README.md`, `BUILDING.md` |
| Sister-tool pin or flake output change | `BUILDING.md` |
| Changed testing rules or layout | `TESTING.md` and §3 of this file |

Additional rules:
- Documentation must describe **implemented** behaviour. Where something is
  designed but not yet implemented, say so explicitly on the page rather than
  documenting it as available.
- Do not include change history, release notes, or "recently added" wording in
  documentation — that belongs in git.
- Update existing pages in place rather than adding parallel pages that
  duplicate them; remove documentation for removed features in the same task.
- If you detect a code/documentation mismatch, follow §9.5: warn the user and
  offer to resolve it. **Never** silently leave a mismatch.

- If you detect a code/documentation mismatch:
  - Explicitly warn the user.
  - Offer to update the documentation to match the code (or the code to match the documentation).
- **Never** silently leave mismatches unresolved.

## 12. Clarification Triggers

Ask the user when:
- Requirements are ambiguous or contradictory.
- A change affects public APIs, file formats, or backwards compatibility.
- Multiple valid approaches exist with significantly different trade-offs.
- A task may have security, licensing, or performance implications.
- The specification is silent or ambiguous on a modulation parameter and the
  choice would affect what ld-decode is being measured against.
